## Prior Home-Decor pass (archive c218) status=partial
ACCESS/METHOD NOTES: SCOPE: per the S.N.218 brief note, scoped strictly to Costco's Home/Decor-relevant category pages (Home Decor rollup + the decor-relevant part of the separate Lighting & Ceiling Light Fixtures line, which Costco's own site files under its Home Improvement department, not Home & Decor - included anyway per this project's universal Lighting-is-in-scope rule, same treatment Target US/S.N.22 and Bed Bath & Beyond/S.N.47 gave their own lighting trees) - did not enumerate Electronics, Grocery, Tires, Furniture, Appliances, Auto, etc.

ACCESS: robots.txt (https://www.costco.com/robots.txt) checked first - no Claude-specific disallow (ClaudeBot/Claude-User/Claude-SearchBot/Claude-Web are not mentioned at all); only generic legacy-WCS view-pattern disallows (CategoryDisplay*, CatalogSearch*, ProductDisplay* etc.), which per Rule 3 are not a block signal. The homepage (https://www.costco.com/) fetches cleanly (HTTP 200, direct urllib, no special headers) every time, confirming the site is live and not retired. However EVERY other path tested this session - every department .html page (home-and-decor.html, furniture.html, appliances.html, electronics.html, patio-lawn-garden.html) and every decor leaf page (mirrors.html, wall-art.html, lighting.html, candles.html, etc.) - is hard-blocked, exhausting Rule 2: (1) direct fetch (urllib, requests, probe.py) -> HTTP 403 'Access Denied' (Akamai edge/WAF block, errors.edgesuite.net reference) on every profile/session, including a session that had just successfully fetched the homepage and carried its Akamai cookies (akavpau_zezxapz5yf, _abck, bm_s/bm_so/bm_sz); (2) curl_cffi impersonation sweep of 19 browser profiles (chrome99/100/110/116/119/120/123/124/131/133a, edge99/101, safari15_3/15_5/17_0/18_0, firefox133/135) - all either the same WAF 403, or (safari15_3/15_5/17_0 specifically) a 200-status Akamai Bot Manager behavioural-sensor interstitial ('sec-if-cpt-container' / 'Powered and protected by Akamai') that requires executing obfuscated JS to pass, which browser automation is off-limits for on this project; (3) r.jina.ai reader proxy -> itself hit a Cloudflare 'Just a moment' managed challenge before ever reaching costco.com; (4) translate.goog (www-costco-com.translate.goog) -> unlike on Bed Bath & Beyond (S.N.47) this side door did reach a genuine costco.com origin (real ServerName/build-number meta tags, Costco favicon) but that origin returned a plain 'Page Not Found!' 404 for every path tried (root, appliances.html, furniture.html, home-and-decor.html alike) - the translate.goog client apparently gets routed to a legacy WCS surface that doesn't recognise the modern Next.js pretty-URL routes, a dead end; (5) WebFetch -> timed out (60s) or ECONNRESET on every department/decor page AND on the homepage itself, so this tool could not reach costco.com at all this session; (6) side doors - sitemap_lw_index.xml/sitemap_lw_c_000.xml (top-level department sitemap) fetch cleanly as plain XML/static assets and were the source of the home-and-decor.html department URL and confirmed the department roster; static Next.js JS bundle chunks also fetch cleanly (200) but contain no client-exposed category/count API endpoint (SSR is server-side only). No Akamai sensor solver exists for this platform (the project's inditex_interstitial_solver.py targets a different, simpler exposed-math-puzzle challenge, not Akamai's obfuscated device-fingerprint sensor used here). Independent confirmation this is a systemic, well-known block: a live web search for scraping guidance on costco.com surfaced multiple 2025-era vendor writeups (ScrapingBee, Unwrangle, Apify) all independently stating Akamai blocks Scrapy/Playwright/Selenium/etc. on costco.com and that JS rendering plus residential proxies are required, matching what was found here - a genuine hard block, not a fixable configuration issue this session, same category of block as the S.N.75 Lowe's precedent (also Akamai) referenced in the brief.
