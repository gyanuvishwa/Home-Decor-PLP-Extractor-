IMPORTANT METHODOLOGY FINDING (differs from the UK/DE sessions): as of this extraction (2026-08-13) the sik.search.blue.cdtapps.com PRIMARY_AREA search API's pagination is non-functional for every market tested (in/en, gb/en, de/de all reproduced) -- the 'size' and 'offset' searchParameters are silently ignored server-side (confirmed via requests, curl_cffi Chrome-124 impersonation, GET variants, and multiple alternate field-name/nesting guesses), every request returns a fixed first-page window of exactly 24 items regardless of what is sent, so the UK/DE sessions' own offset-boundary exhaustion method (offset=max-1 -> 1 item, offset=max -> 0 items) could not be reproduced or reused here; this is a live site-wide API change, not an India-specific gap. In its place an equally rigorous two-signal cross-check was used and applied to EVERY leaf row: (1) the sik.search API's own metadata.itemsPerType.PRODUCT field (a separate server-computed total, decoupled from the 24-item window truncation, and distinct from the raw metadata.max field which was found to sometimes over-count by including non-product 'PLANNER' room-planner-tool tiles mixed into results -- e.g. category 10731 Floor Lamps: max=23 but itemsPerType={PRODUCT:22, PLANNER:1}, true product qty=22); (2) the category page's own SSR-rendered visible total-count text (class plp-filter-information__total-count, e.g. '22 items', matching the 'Showing 24 of N results' progress-bar max on larger categories). Both signals were pulled independently (one via POST to the search API, one via a plain GET of the public category page HTML) and matched EXACTLY on all 58 leaf categories with zero discrepancies -- recorded as qty. This is at least as strong as the UK/DE boundary-offset method: it is the number IKEA's own page displays to every visitor, corroborated by the backend's own per-type product count, rather than an unverified raw API total. NOTE ON A LIKELY PRE-EXISTING UK/DE INACCURACY (flagged for awareness only, out of scope to correct retroactively): the UK (c100) and DE (c117) archives used raw metadata.max directly (e.g. UK Floor Lamps qty=40), which on inspection appears to have silently included a PLANNER tile in at least that category (itemsPerType breakdown unavailable retroactively for the historical UK/DE runs, but the same API when queried live today for UK cat 10731 returns max=40 with itemsPerType={PRODUCT:39, PLANNER:1}); India's rows here use the corrected PRODUCT-only count throughout.
