The genuine, live, actively-maintained HKliving brand site is hkliving.com (no dash; confirmed via web search as 'the official HKliving website', Cloudflare-fronted, live Umbraco/VWA CMS site, title 'HKLIVING: Creating ambience'). SITE NATURE: hkliving.com is a B2B/wholesale-facing trade catalogue (nav: 'Become a dealer', 'Agents & Distributors', 'Where can I buy HKLIVING?' -> store locator; no visible prices/checkout) rather than a direct consumer webshop -- matches the brief's boutique/designer-brand note. Product browsing and category counts are fully public with no login/dealer-account wall encountered.

ACCESS METHOD: category pages render their product grid client-side via an Umbraco AJAX endpoint, /umbraco/surface/AsyncContentSurface/Index (POST, JSON), driven by a categoryId read from each page's hidden #__CategoryId input plus a per-session CSRF RequestVerificationToken (cookie + hidden-field pair). Direct static HTML fetch shows only 'Loading filter please wait...' with no counts; replaying the real AJAX call (session cookies + token + categoryId, doGroupProducts=1 matching the page's own default) returns JSON whose articlelist_container HTML includes a '<span class="totalcount">N</span>' -- the exact number the site itself renders next to the 'Filter products' button for a real visitor. All qty values below are this totalcount field.

VERIFICATION (Rule 1): counting rendered <article> tiles/hrefs was explicitly NOT used as primary evidence -- confirmed unreliable here exactly as the project has seen elsewhere: Mirrors showed 15 grouped swatch-cards for totalcount=16 because one card bundles 2 distinct colour SKUs (dressing-table-mirror-petrol + -candy) under one swatch selector (15 cards - 1 + 2 = 16, reconciles exactly); Pendant Lamps showed 16 tiles on page 1 for totalcount=17, and page 2 (PageIndex=1) returned exactly 1 further article, confirming full pagination exhaustion (16+1=17).
