ACCESS/METHOD NOTES: Access: direct fetch worked throughout (no WAF/challenge, robots.txt has generic Disallow: / with explicit Allow for /, /products/, /collections/ etc - no Claude-specific block). Site is a headless Next.js storefront over a Shopify backend (cdn.shopify.com assets) - standard /collections/<handle>/products.json is NOT exposed (404), so Rule 1's usual 'enumerate via products.json' route is unavailable. Verification method used instead: each collection page renders a genuine 'N Products' summary AND real server-rendered pagination (?page=2..M); page size is a fixed 20/page confirmed from the embedded grid JSON (product 'handle' fields in the RSC payload, e.g. clocks page 1 = exactly 20 distinct handles). For every extracted category I performed an exhaustion check: ceil(displayed_count/20) was compared to the actual last pagination link on the page, and all 19 matched exactly (e.g. Lamps & Lighting 10311 Products -> last link page=516 = ceil(10311/20); Serveware 8285 -> page=415; Wall Decor 20224 -> page=1012; Clocks 2052 -> page=103; etc). This is a real per-collection exhaustion check, not a trust of a raw inflatable field - counts treated as verified. Large counts are explained (and cross-checked) by the sitemap: sitemap.xml lists 36 sitemap_products_N.xml files (35 x 2500 + 1 x 885 = ~88,385 total product URLs sitewide), and product-detail sampling confirmed the site models each colour/variant as a SEPARATE product page (e.g. Ashtrays: barca-ash-tray, barca-ash-tray-blue, barca-ash-tray-green, barca-ash-tray-purple = 4 distinct product URLs for one design) - this is why single categories like Lamps & Lighting (10311) or Wall Decor (20224) run into five figures; it is a real count of real distinct listed product pages, not a products_count API artifact.
